R2-3 AgentCore 앱: 같은 agent와 skill을 Claude Code 밖에서 돌리기

설치한 my-kit의 agent 지침과 skill 파일을 고치지 않고 Amazon Bedrock AgentCore harness에 올려, 터미널 명령과 작은 Python 앱으로 호출한 뒤, 만든 리소스를 모두 지운다

R2-1, R2-2는 Claude Code 안에서 plugin을 썼습니다. 이 미션은 같은 지침을 AgentCore harness(모델, 시스템 프롬프트, 도구를 설정 파일로 정하면 AgentCore가 에이전트 루프를 돌려 주는 방식)에 올려, Claude Code를 열지 않고도 같은 형식의 리포트가 나오는지 봅니다. 선택 미션이고, 고르면 R2 미션 두 개 중 하나로 셉니다. 실습 EC2는 Administrator 권한이라 배포가 막히지 않는 대신, 지우는 일도 직접 해야 합니다. 그래서 배포보다 먼저 비용이 드는 명령은 확인받는 규칙을 두고, 마지막에 정리를 합니다.

선택 미션 안내와 준비

10분

이 미션을 고를지 정하고, AgentCore CLI와 AWS 자격 증명, 근거로 쓸 리포트를 확인합니다.

항목내용
세는 방법선택 미션입니다. 고르면 R2 미션 두 개 중 하나로 셉니다(R2-1 + R2-3, 또는 R2-2 + R2-3). 고르지 않아도 완주입니다.
올리는 것설치된 my-kit의 agent 두 개(COLLECT, REVIEW) 지침과 skills/의 SKILL.md. 파일은 고치지 않고 harness의 시스템 프롬프트에 그대로 붙입니다.
올리지 않는 것MCP 서버, 훅, API 키. harness에는 Claude Code의 subagent, 훅, plugin MCP 서버가 없어서, 이 미션은 자료를 프롬프트에 담아 보냅니다(트랙 B는 sample.json mock, 트랙 A와 C는 R2에서 만든 리포트).
만들어지는 AWS 리소스AgentCore harness 하나와 그것을 돌리는 Runtime, 실행 역할(IAM), CloudFormation 스택, CloudWatch 로그. 처음 배포하면 CDK bootstrap 스택도 생깁니다. 04 정리에서 지웁니다.

왜 필요한가요: 배포는 내 AWS 계정에 리소스를 만듭니다. CLI 버전(v1), 실습 계정, harness를 지원하는 리전이 맞아야 배포와 정리가 이 페이지의 명령대로 됩니다.

먼저 이 미션 전체에서 무엇이 만들어지고 지워지는지 그림으로 봅니다. 아이콘은 AWS 서비스(CloudFormation, AgentCore, Bedrock)입니다.

1도구와 자격 증명 확인

Claude 세션 밖의 터미널에서 실행합니다. AgentCore CLI는 npm 패키지라 Node.js 20.12 이상이 필요합니다 (AgentCore CLI 시작하기). 이 페이지의 명령은 CLI v1 기준입니다.

Terminal, 전체 복사
node --version
command -v agentcore || npm install -g --prefix "$HOME/.local" @aws/agentcore
agentcore --version
command -v uv || { curl -LsSf https://astral.sh/uv/install.sh | env UV_INSTALL_DIR="$HOME/.local/bin" sh; export PATH="$HOME/.local/bin:$PATH"; }
uv --version
aws sts get-caller-identity
echo "region=${AWS_REGION:-$(aws configure get region)}"

agentcore --version이 1로 시작하는 버전을 내고, get-caller-identity가 실습 계정을 보여 주면 됩니다. 리전은 AgentCore harness를 지원하는 곳이어야 합니다. 서울(ap-northeast-2), 도쿄, 버지니아 북부, 오레곤 등이 지원하고, 목록은 지원 리전 표의 AgentCore harness 줄에서 봅니다.

2작업 폴더와 근거 리포트

AgentCore 프로젝트는 capstone-try 밖의 새 폴더에 만듭니다. capstone-try는 R2 공통 04에서 my-kit 말고 다른 plugin을 모두 꺼 두었고, 재사용 확인(kit.sha, find)에 다른 파일이 섞이지 않아야 하기 때문입니다. 새 폴더에서는 Setup에서 설치한 aws-agents plugin이 켜져 있습니다.

Terminal, 전체 복사
mkdir -p ~/claude-lab/capstone-agentcore && cd ~/claude-lab/capstone-agentcore
. ~/claude-lab/capstone/r2.env && echo "KIT=$KIT TRACK=$TRACK COLLECT=$COLLECT REVIEW=$REVIEW"
ls ~/claude-lab/capstone/marketplace/plugins/$KIT/agents ~/claude-lab/capstone/marketplace/plugins/$KIT/skills
ls -t ~/claude-lab/capstone-try/reports/
claude plugin list --json | jq -r '.[] | select(.id | startswith("aws-agents@")) | "\(.id) \(.enabled)"'

agent 파일에 $COLLECT, $REVIEW 이름이 보이고, reports/에 리포트가 하나 이상 있어야 합니다. 리포트가 없으면 capstone-try의 세션에서 R2-1 01 표의 첫 번째 명령 하나만 먼저 보냅니다. 마지막 줄이 aws-agents@claude-plugins-official true가 아니면 Setup 필수 설치로 돌아갑니다.

aws-agents plugin은 막혔을 때 씁니다 이 폴더의 Claude 세션에서 /aws-agents:agents-debug(CLI나 자격 증명 문제), /aws-agents:agents-deploy(배포 실패 진단)에 오류 메시지를 붙여 넣으면 원인을 짚어 줍니다. 이 plugin의 안내에는 CLI v0의 옵션(agentcore create --framework, --defaults)이 섞여 있습니다. 명령은 이 페이지와 CLI v1 변경 사항을 따릅니다.

01

가드레일: 지우거나 비용이 드는 AWS 명령은 확인받기

5분

Administrator 권한에서는 Claude가 AWS를 바꾸는 명령도 막힘없이 실행됩니다. 배포하기 전에, 이 폴더에서 그런 명령은 매번 묻도록 권한 ask 규칙을 둡니다.

왜 필요한가요: 02의 배포와 04의 정리를 Claude에게 맡겨도, 리소스를 만들거나 지우는 순간에는 사람이 명령을 읽고 승인하게 됩니다.

Terminal, 전체 복사
mkdir -p ~/claude-lab/capstone-agentcore/.claude && cd ~/claude-lab/capstone-agentcore
cat > .claude/settings.json << 'EOF'
{
  "permissions": {
    "ask": [
      "Bash(agentcore deploy *)",
      "Bash(agentcore dev *)",
      "Bash(agentcore invoke *)",
      "Bash(agentcore remove *)",
      "Bash(npx cdk destroy *)",
      "Bash(aws cloudformation delete-stack *)",
      "Bash(aws logs delete-log-group *)",
      "Bash(aws bedrock-agentcore-control delete-*)",
      "Bash(aws ec2 run-instances *)",
      "Bash(aws ec2 terminate-instances *)"
    ]
  }
}
EOF
jq -r '.permissions.ask[]' .claude/settings.json
규칙왜 묻나
agentcore deploy, agentcore devAWS 리소스를 만들거나 바꿉니다. harness 프로젝트의 agentcore dev --mode browser도 배포부터 하고 클라우드에서 호출합니다
agentcore invoke부를 때마다 Runtime 세션과 모델 토큰 비용이 듭니다. 03에서는 사람이 터미널에서 직접 부르므로 묻지 않고, Claude가 부르려 할 때만 묻습니다
agentcore remove, npx cdk destroy, delete-stack, delete-log-group, delete-*지운 것은 되돌릴 수 없습니다. 정리는 사람이 보고 승인합니다
aws ec2 run-instances, terminate-instances이 미션 밖의 예입니다. 비용이 크거나 지우는 명령을 같은 모양으로 더 적어 넣습니다

규칙은 deny, ask, allow 순으로 보고, 맞는 ask 규칙이 있으면 더 좁은 allow 규칙이 있어도 묻습니다. *는 하위 명령(deploy, delete-stack) 뒤에 둡니다. cd 폴더 && agentcore deploy처럼 이어 쓴 명령도 부분마다 검사하고, auto 모드에서도 묻습니다. 다만 규칙은 Claude가 쓴 명령 글자를 보는 것이라 sh -c '…'나 절대 경로 실행처럼 다른 모양은 잡지 못하고, bypassPermissions 모드에서는 묻지 않습니다. 보안 경계가 아니라 실수를 막는 한 겹입니다 (권한 공식 문서).

규칙이 걸리는지 봅니다. 이 폴더에서 세션을 열고 지우는 명령을 시킨 뒤, 확인 창이 뜨면 No를 고릅니다.

Terminal
cd ~/claude-lab/capstone-agentcore && claude
Claude 세션 입력
Bash 도구로 agentcore remove all --yes 를 실행해 주세요.

명령을 실행하기 전에 승인을 묻는 창이 떠야 합니다. No를 고르면 아무것도 바뀌지 않습니다. /permissions를 입력하면 ask 규칙 목록과 그 규칙이 들어 있는 파일(.claude/settings.json)이 보입니다. 확인했으면 세션을 닫습니다.

02

같은 agent와 skill을 AgentCore에 올리기

20분

빈 AgentCore 프로젝트에 harness 하나를 더하고, 시스템 프롬프트에 my-kit의 agent 지침과 SKILL.md를 그대로 붙여 배포합니다.

왜 필요한가요: harness에는 Claude Code의 subagent, 훅, plugin MCP 서버가 없습니다. 그래서 agent 지침과 skill(절차와 출력 형식을 적은 SKILL.md)을 시스템 프롬프트에 그대로 붙여 같은 지침을 씁니다.

1프로젝트와 harness 만들기

빈 프로젝트(--template empty)를 만들고 agentcore add harness로 harness를 더합니다. 메모리는 이 미션에 필요 없으니 끕니다. 모델을 적지 않으면 CLI가 정한 Bedrock 기본 모델이 harness.yaml에 들어갑니다 (모델과 지침 공식 문서).

Terminal, 전체 복사
cd ~/claude-lab/capstone-agentcore
agentcore create --name CapstoneApp --template empty
cd CapstoneApp
agentcore add harness --name capstone_app \
  --system-prompt "임시 지침입니다. 다음 블록에서 바꿉니다." \
  --memory '{"mode":"disabled"}'
sed -i 's/^    # maxTokens: 4096/    maxTokens: 16000/' app/capstone_app/harness.yaml
grep -n 'maxTokens: 16000' app/capstone_app/harness.yaml
ls app/capstone_app
cat agentcore/aws-targets.json

sed 줄은 harness.yaml에 주석으로 들어 있는 모델 출력 한도(maxTokens)를 켜서 16000으로 올립니다. 기본값으로 두면 정기 리포트처럼 긴 답이 중간에 Model stopped generating due to maximum token limit로 끊깁니다. 다음 줄에 maxTokens: 16000이 한 줄 보여야 합니다. 실습 PC에서는 agentcore add harness --max-tokens로는 이 오류가 사라지지 않았습니다. grep 결과가 한 줄도 나오지 않으면 harness.yaml의 model.bedrockModelConfig 아래에 maxTokens: 16000 한 줄을 직접 넣습니다(modelId와 같은 들여쓰기).

app/capstone_app/에 harness.yaml과 system-prompt.md가 보여야 합니다. aws-targets.json의 계정과 리전이 00에서 본 값과 다르면 그 파일의 값을 고칩니다. 리전이 어긋나는 것이 배포 실패의 가장 흔한 원인입니다.

2시스템 프롬프트에 agent와 skill 붙이기

마켓플레이스에 올린 my-kit에서 agent 두 개의 본문(앞머리 frontmatter 제외)과 SKILL.md 전체를 그대로 이어 붙입니다. 맨 앞 몇 줄은 Claude Code와 다른 점을 알려 주는 안내입니다. skill의 "my-kit:이름 에이전트에게 맡깁니다" 단계는 이 안내에 따라 같은 이름의 역할 지침으로 직접 수행됩니다.

Terminal, 전체 복사
cd ~/claude-lab/capstone-agentcore/CapstoneApp && . ~/claude-lab/capstone/r2.env
P=~/claude-lab/capstone/marketplace/plugins/$KIT
{
  echo "# ${KIT} 업무 에이전트 (AgentCore harness)"
  echo "이 환경에는 Claude Code의 subagent, 훅, MCP 도구가 없습니다."
  echo "아래 skill에서 '${KIT}:이름 에이전트에게 맡깁니다'라고 적힌 단계는, '역할: ${KIT}:이름' 절의 지침을 따라 직접 수행합니다."
  echo "자료는 사용자가 메시지에 준 것만 씁니다. 파일에 저장하라는 단계는 응답 본문으로 출력하는 것으로 대신합니다."
  for a in "$COLLECT" "$REVIEW"; do
    echo; echo "## 역할: ${KIT}:$a"
    awk 'n >= 2 { print; next } /^---$/ { n++ }' "$P/agents/$a.md"
  done
  for s in "$P"/skills/*/SKILL.md; do
    echo; echo "## skill 파일: $(basename "$(dirname "$s")")/SKILL.md"
    cat "$s"
  done
} > app/capstone_app/system-prompt.md
grep -E '^## ' app/capstone_app/system-prompt.md
wc -c app/capstone_app/system-prompt.md

## 역할: 줄 두 개와 ## skill 파일: 줄(R2 공통 01에서 만든 skill 수만큼)이 보이면 됩니다. agent의 tools: 줄은 frontmatter에 있어 빠지고, 지침 본문만 들어갑니다. 원본 파일은 읽기만 했으므로 지문(kit.sha)은 그대로입니다.

skill을 skill로 붙이는 방법도 있습니다 harness는 SKILL.md 폴더를 S3, Git 저장소, AWS 제공 skill에서 받아 필요할 때만 읽는 기능도 있습니다 (harness skills 공식 문서). S3 버킷이나 공개 저장소가 하나 더 생기고 실행 역할 권한도 봐야 해서, 이 미션은 리소스가 가장 적은 시스템 프롬프트 방식을 씁니다. R2 공통 01에서 frontmatter를 name과 description만 쓴 덕분에 두 방식 모두 같은 파일을 그대로 씁니다.
3키와 개인정보가 없는지 보고 배포

시스템 프롬프트는 배포하면 AWS에 저장됩니다. 서울 열린데이터 키, Alpha Vantage 키 같은 값이 들어가면 안 됩니다. R2-2 04와 같은 검사를 이 폴더에 돌립니다.

Terminal, 전체 복사
cd ~/claude-lab/capstone-agentcore/CapstoneApp
grep -nE '(^|[^0-9])([0-9]{6}-[1-4][0-9]{6}|[0-9]{4}-[0-9]{4}-[0-9]{4}-[0-9]{4}|01[016789]-[0-9]{3,4}-[0-9]{4})([^0-9]|$)' app/capstone_app/* || echo "개인정보 패턴 없음"
jq -r '.. | objects | (.SEOUL_API_KEY?, .ALPHA_VANTAGE_API_KEY?, .Authorization?) | strings | sub("^Bearer "; "")' ~/.claude.json 2>/dev/null \
  | while IFS= read -r V; do [ ${#V} -ge 8 ] && grep -rlF -- "$V" app/ agentcore/aws-targets.json ; done
echo "키 검사 끝 (위에 파일 이름이 나오면 그 파일에 키나 토큰이 있습니다)"

파일 이름이 나오면 배포하지 말고 그 파일부터 고칩니다. 아무것도 나오지 않았으면 배포합니다. agentcore deploy는 CDK로 리소스를 만들고, 확인을 물으면 내용을 보고 승인합니다. 처음 배포는 계정에 CDK bootstrap을 하느라 몇 분 걸립니다. 끝나면 상태를 봅니다.

agentcore deploy는 추적을 보려고 계정 전체의 CloudWatch Transaction Search를 켭니다. 프로젝트 리소스가 아닌 계정 설정이라 04 정리 뒤에도 켜진 채 남습니다. 공유 계정이라 켜고 싶지 않으면 배포 전에 agentcore config transactionSearch false를 실행합니다 (harness 관측과 비용 공식 문서).

Terminal, 전체 복사
cd ~/claude-lab/capstone-agentcore/CapstoneApp
agentcore deploy
agentcore status

출력에서 harness의 ARN(arn:aws:bedrock-agentcore:리전:계정:harness/…)을 찾아 둡니다. 03과 04에서 씁니다.

키는 AgentCore에 넘기지 않습니다 이 미션의 harness는 외부 API를 부르지 않고, 메시지로 받은 자료만 씁니다. 트랙 B는 sample.json(합성 데이터, mock)을, 트랙 A와 C는 이미 검사를 거친 리포트를 보냅니다. 나중에 실데이터 API를 붙이려면 키를 시스템 프롬프트나 코드에 넣지 말고, 공식 문서가 안내하는 AgentCore Identity의 token vault(API 키 보관소)에 둡니다 (모델과 지침 공식 문서). 그 연결은 이 미션 범위 밖입니다.

3작은 Python 앱으로 호출

같은 harness를 다른 프로그램에서도 부를 수 있는지 봅니다. 공식 문서의 boto3 예제(invoke_harness)를 파일 하나로 옮긴 것입니다. 02에서 찾은 ARN을 첫 줄에 붙여 넣습니다.

Terminal, ARN을 바꿔서 전체 복사
cd ~/claude-lab/capstone-agentcore
echo 'HARNESS_ARN=arn:aws:bedrock-agentcore:리전:계정:harness/여기에-ID' > app.env
cat > ask_app.py << 'EOF'
import os, sys, uuid
import boto3

arn = os.environ["HARNESS_ARN"]
client = boto3.client("bedrock-agentcore", region_name=arn.split(":")[3])
text = open(sys.argv[1], encoding="utf-8").read()
response = client.invoke_harness(
    harnessArn=arn,
    runtimeSessionId=str(uuid.uuid4()),
    messages=[{"role": "user", "content": [{"text": text}]}],
)
for event in response["stream"]:
    if "contentBlockDelta" in event:
        delta = event["contentBlockDelta"].get("delta", {})
        if "text" in delta:
            print(delta["text"], end="", flush=True)
    elif "runtimeClientError" in event:
        print(f"\nError: {event['runtimeClientError']['message']}")
print()
EOF
set -a; . ./app.env; set +a
uv run --no-project --quiet --with boto3 python ask_app.py input.txt | tee out-app.md

리포트가 글자 단위로 흘러나오고 out-app.md에 남습니다. 세션 ID는 33자 이상이어야 해서 UUID를 씁니다. 같은 자료로 CLI와 앱 두 번 불렀으니 내용은 조금 달라도 형식은 같아야 합니다.

정리: 만든 AgentCore 리소스 지우기

10분

프로젝트의 모든 리소스를 지우고, 남은 것이 없는지 확인합니다. 출품할 캡처는 지우기 전에 받아 둡니다(05의 양식 5번).

지우지 않으면 비용이 남습니다 harness 자체에는 추가 요금이 없고, harness가 쓰는 기능의 표준 요금을 냅니다. AgentCore Runtime은 harness 세션마다 microVM을 띄우고, 실제로 쓴 CPU와 초마다의 최대 메모리를 과금합니다. 모델이나 도구 응답을 기다리는 동안은 CPU 요금이 붙지 않지만, 메모리는 세션이 살아 있는 동안 계속 과금됩니다. 마지막 호출 뒤에도 쉬는 세션은 idleRuntimeSessionTimeout(기본 900초)까지 남습니다. 여기에 호출마다 모델 토큰 비용(시스템 프롬프트 포함)과, 호출마다 쌓이는 CloudWatch 추적, 로그, 지표 비용이 따로 듭니다 (harness 비용 공식 문서, AgentCore 요금). 미션이 끝나면 바로 지웁니다.

왜 필요한가요: 실습 EC2는 Administrator 권한이라 배포가 막히지 않는 대신, 지우는 일도 직접 해야 합니다. 남겨 둔 리소스는 위 상자처럼 비용이 됩니다.

1지우기
Terminal, 전체 복사
cd ~/claude-lab/capstone-agentcore/CapstoneApp
agentcore remove all --yes
agentcore deploy --yes
agentcore status

remove all은 프로젝트 명세에서 모든 리소스를 빼고, 이어지는 deploy가 빈 상태를 보고 배포된 스택을 내립니다 (CLI 정리 공식 문서). 이 두 줄을 Claude 세션에 맡기면 01의 ask 규칙 때문에 줄마다 승인을 묻습니다. 그때는 명령을 읽고 Yes를 고릅니다.

2남은 것 확인
Terminal, 전체 복사
cd ~/claude-lab/capstone-agentcore && set -a; . ./app.env; set +a
REGION=$(echo "$HARNESS_ARN" | cut -d: -f4) && echo "region=$REGION"
aws bedrock-agentcore-control list-harnesses --region "$REGION" \
  --query "harnesses[?contains(harnessName, 'capstone_app')].[harnessName,status]" --output text
aws cloudformation list-stacks --region "$REGION" \
  --query 'StackSummaries[?StackStatus!=`"DELETE_COMPLETE"` && contains(StackName, `"CapstoneApp"`)].[StackName,StackStatus]' --output text
aws logs describe-log-groups --region "$REGION" \
  --log-group-name-prefix /aws/bedrock-agentcore/ \
  --query "logGroups[].logGroupName"
확인정상남아 있으면
list-harnesses아무 줄도 나오지 않음한 줄이라도 나오면 남아 있는 것입니다(이름 앞에 프로젝트 이름이 붙어 있을 수 있음). DELETING이면 몇 분 뒤 다시 보고, DELETE_FAILED이거나 30분 넘게 DELETING이면 그 줄을 운영진에게 보여 줍니다
list-stacks아무 줄도 나오지 않음한 줄이라도 나오면 남아 있는 것입니다. DELETE_IN_PROGRESS면 기다렸다 다시 보고, DELETE_FAILED, ROLLBACK_COMPLETE, UPDATE_ROLLBACK_COMPLETE, CREATE_COMPLETE 등이면 agentcore deploy --yes를 한 번 더 실행하고, 그래도 남으면 aws cloudformation delete-stack --stack-name 스택이름(ask 규칙이 묻습니다) 후 같은 확인을 반복합니다
describe-log-groups이 미션에서 생긴 로그 그룹이 없음스택을 지워도 로그 그룹은 남습니다. 오늘 만든 것만 aws logs delete-log-group --log-group-name 이름으로 지웁니다. 다른 실습의 로그 그룹은 건드리지 않습니다

CLI는 스택 이름을 AgentCore-프로젝트이름-배포대상이름으로 짓습니다(agentcore-cli 소스). 그래서 CapstoneApp을 찾습니다. 프로젝트 이름을 바꿨다면 그 이름으로 찾고, 확실하지 않으면 --query의 contains 조건을 빼고 AgentCore-로 시작하는 스택을 봅니다. CDK bootstrap 스택(CDKToolkit)은 계정의 다른 CDK 배포가 함께 쓰므로 지우지 않습니다. list-harnesses가 알 수 없는 명령이라고 나오면 AWS CLI가 오래된 것이니, agentcore status와 list-stacks 결과로 확인합니다. 로컬 파일(CapstoneApp/, input.txt, out-*.md)은 AWS 비용과 상관없으니 필요하면 남겨 둡니다.
