Ch2 Lab 1. 정책 배포

Hands-on Lab / Chapter 2, Lab 1

Claude Code Deep Dive Workshop, Chapter 2 Lab 1 - Bedrock 위에서 안전하게 쓰기, 정책 배포 실습

Ch2 강의에서 본 Bedrock 배포의 뼈대를 이 환경에서 그대로 읽고, managed-settings.json으로 조직 정책을 직접 배포합니다. 이 ccb-endpoint는 이미 Bedrock에 연결되어 있으니, 연결 자체보다 "무엇이 어떻게 설정되어 있고, 사용자가 무엇을 바꿀 수 없는가"에 집중합니다.

이번 랩의 역할은 IT보안·플랫폼 담당자입니다. 고객자산 분석팀이 Claude Code를 쓰기 시작하는데, 원본 고객 데이터(raw/)는 읽지 못하게 막아 달라는 요청이 왔습니다. 정책 파일 한 장으로 이 요청을 처리합니다.

소요 시간 50분 내외 · Task 준비 + 6개 · 기준 버전 Claude Code 2.1.x · Update 2026.11

ℹ

이 랩은 sudo를 씁니다

/etc/claude-code/managed-settings.json은 시스템 경로입니다. ccb-endpoint의 ec2-user는 sudo를 쓸 수 있습니다. 회사 PC라면 같은 파일을 MDM이나 배포 도구로 내려보냅니다.

TASK 00 · 사전 준비 확인 (2분)

ℹ

Ch1까지 마치지 못했다면, 먼저 catchup

앞 랩이 중간에 실패했거나 건너뛰었다면, 실행 중인 claude를 모두 종료한 뒤 아래 한 줄로 이 랩을 시작할 수 있는 상태를 맞추고 TASK 00 블록을 실행합니다. 앞 랩을 마쳤다면 건너뜁니다.

bash
catchup ch2
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. catchup ch2는 남은 정책(managed-settings)을 ~/claude-lab/.catchup-backup/에 복사해 둔 뒤 비우고, 사용자 설정에서 Ch2 Lab 1의 raw 읽기 규칙과 Ch2 Lab 2의 permissions.ask·autoMode를 지우고(이전 파일은 settings.json.before-catchup으로 남김), 기본 모드(use_bedrock_direct)로 돌립니다. 이 랩의 작업 폴더 ~/claude-lab/ch2가 이미 있으면 지우지 않고 ~/claude-lab/.catchup-backup/으로 옮깁니다. Ch4에서 설치하는 asset-team-kit 플러그인과 fsi-local 마켓플레이스가 등록되어 있으면 제거합니다. 이 랩을 시작할 때는 없는 상태이기 때문입니다. 채워 넣을 앞 랩 결과물은 없습니다.

catchup: command not found가 나오면 아래 블록으로 같은 스크립트를 받아 실행합니다.

bash
bash <(curl -fsSL https://www.atomai.click/claude-code-workshop/20261116/assets/catchup.sh) ch2
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. curl -fsSL이 워크숍 사이트에서 catchup 스크립트를 받고(-f는 오류 페이지를 받지 않음, -s는 진행 표시를 숨기되 -S로 오류는 보여 주고, -L은 리디렉션을 따라감), bash <(…) ch2가 받은 스크립트를 ch2를 인자로 실행합니다. <( )는 명령의 출력을 파일처럼 넘기는 bash 문법이라, 스크립트 안의 sudo나 claude가 입력을 읽어도 스크립트가 중간에 끊기지 않습니다. 하는 일은 위 블록과 같습니다.

분석팀 PC에 있는 두 폴더를 작업 폴더에 연결해 둡니다. raw/는 막을 대상이고 pseudo/는 열어 줄 대상입니다. Preflight에서 데이터를 이미 받았다면 키트 내려받기 줄은 아무 일도 하지 않습니다.

Terminal, 전체 복사

bash
use_bedrock_direct >/dev/null
KIT=${WS_KIT:-s3://ws-assets-prod-iad-r-iad-ed304a55c2ca1aee/5b8d0649-9ad2-43a8-8ff5-10ce7bb42e6f/mydata-kit.zip}
[ -d ~/claude-lab/mydata/pseudo ] || (aws s3 cp "$KIT" /tmp/mydata-kit.zip --only-show-errors && mkdir -p ~/claude-lab/mydata && unzip -qo /tmp/mydata-kit.zip -d ~/claude-lab/mydata)
mkdir -p ~/claude-lab/ch2 && cd ~/claude-lab/ch2 && git init -q
ln -sfn ~/claude-lab/mydata/raw raw
ln -sfn ~/claude-lab/mydata/pseudo pseudo
sudo jq -e 'del(.forceLoginMethod, .forceLoginGatewayUrl) == {}' /etc/claude-code/managed-settings.json >/dev/null \
  && echo "정책 상태: 깨끗함" || echo "경고: 이전 챕터 정책이 남아 있습니다. 아래 '정책 초기화'를 먼저 실행하세요"
sudo cp /etc/claude-code/managed-settings.json ~/claude-lab/ch2/managed-settings.backup.json
ls -l
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. use_bedrock_direct는 이 PC를 기본 모드(Bedrock 직접 연결)로 맞추는 도우미 명령입니다. 이전 챕터에서 게이트웨이 모드로 바꿨다면 되돌립니다. >/dev/null은 화면에 나오는 메시지를 버립니다.
  2. 키트가 있는 S3 주소를 KIT 변수에 담고, ~/claude-lab/mydata/pseudo 폴더가 없을 때만 내려받아 풉니다. [ -d … ] ||는 "폴더가 없으면 뒤를 실행"이라는 뜻입니다. WS_KIT는 실습 환경이 미리 넣어 둔 이 이벤트의 키트 주소입니다. 이 값이 비어 있을 때만 :- 뒤의 공개 사본 주소를 씁니다.
  3. 분석팀 작업 폴더 ch2를 만들고 그 안에서 git 저장소를 시작합니다. &&는 앞 명령이 성공했을 때만 다음을 실행합니다.
  4. ln -sfn은 바로가기(심볼릭 링크)를 만듭니다. ch2 안의 raw와 pseudo가 mydata의 실제 폴더를 가리킵니다. 그래서 TASK 02의 deny에 실제 경로와 링크 경로를 둘 다 넣습니다.
  5. managed-settings에 이전 챕터의 흔적이 있는지 확인합니다. sudo는 관리자 권한으로 실행하라는 뜻입니다. jq -e는 결과가 거짓이면 실패로 끝나고, del(…) == {}는 게이트웨이용 키 두 개를 빼면 파일이 빈 {}인지 묻습니다. 참이면 "깨끗함", 아니면 경고를 출력합니다. 줄 끝의 \는 다음 줄과 이어진 한 명령이라는 표시입니다.
  6. 지금 managed-settings를 managed-settings.backup.json으로 복사해 둡니다(TASK 05에서 되돌릴 때 씁니다). 마지막으로 폴더 내용을 길게 나열해 링크가 만들어졌는지 확인합니다.
⚠

"이전 챕터 정책이 남아 있습니다"가 나오면, 정책 초기화

이전 챕터의 원복을 건너뛰면 그 정책이 이번 챕터의 백업에 섞여 들어가고, 원복해도 계속 남습니다(예: Opus를 뺀 모델 목록). 백업 전에 아래로 초기화한 뒤 위 블록을 다시 실행하세요.

bash
echo '{}' | sudo tee /etc/claude-code/managed-settings.json >/dev/null
sudo rm -f /etc/claude-code/managed-settings.d/*.json
use_bedrock_direct
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. 빈 JSON {}를 managed-settings 파일에 씁니다. tee는 받은 글을 파일에 쓰는 명령입니다. > 리다이렉트는 내 계정으로 처리되어 /etc에 쓸 수 없으니, 쓰는 쪽인 tee에 sudo를 붙입니다.
  2. managed-settings.d/ 안의 조각 파일(.json)을 모두 지웁니다. -f는 파일이 없어도 오류를 내지 않습니다.
  3. 기본 모드로 되돌리는 도우미 명령을 다시 실행합니다. 이 명령은 ~/.claude/settings.json에서 모드 키(env, availableModels, fallbackModel, model, tui)만 바꾸고 플러그인 켜기 상태, 상태줄, 훅과 권한 규칙은 그대로 둡니다.

TASK 01 · 지금의 연결을 해부하기 (7분)

먼저 질문 하나가 Bedrock의 모델에 닿는 길을 그림으로 봅니다. 아래 Step에서 이 길의 각 부분을 설정 파일과 명령으로 확인합니다.

Step 1 · 연결 설정 읽기

Terminal, 전체 복사

bash
jq '{availableModels, env: (.env | with_entries(select(.key | test("BEDROCK|AWS_REGION|ANTHROPIC"))))}' ~/.claude/settings.json
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. jq는 JSON 파일에서 원하는 부분만 뽑아 보는 명령입니다. 이 식은 새 JSON을 만들면서 availableModels 값을 그대로 가져옵니다.
  2. .env | with_entries(select(.key | test("BEDROCK|AWS_REGION|ANTHROPIC")))는 env 안의 항목 중 이름에 BEDROCK, AWS_REGION, ANTHROPIC이 들어간 것만 남깁니다. 끝의 파일 이름이 읽을 대상입니다.
키 이 환경의 값 의미
CLAUDE_CODE_USE_BEDROCK 1 Bedrock 공급자 사용
AWS_REGION us-east-1 호출 리전
ANTHROPIC_DEFAULT_*_MODEL global.anthropic.claude-*-5-5 모델 버전 고정 (global 추론 프로파일)
availableModels opus, sonnet, haiku /model 선택지 제한
⚠

모델을 고정하지 않으면

Bedrock의 기본 주 모델은 Opus 5.5이고 Opus 단가로 청구됩니다. 여러 사용자에게 배포할 때는 이 환경처럼 반드시 ANTHROPIC_DEFAULT_*_MODEL을 고정합니다.

Step 2 · 이 계정에서 쓸 수 있는 추론 프로파일

Terminal, 전체 복사

bash
aws bedrock list-inference-profiles --region us-east-1 \
  --query "inferenceProfileSummaries[?contains(inferenceProfileId,'anthropic.claude')].inferenceProfileId" \
  --output text | tr '\t' '\n' | grep -E '5-5' | sort
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. Bedrock에 추론 프로파일 목록을 us-east-1 리전에서 물어봅니다. 줄 끝의 \는 다음 줄로 이어진다는 표시입니다.
  2. --query는 응답에서 필요한 값만 고르는 식입니다. 프로파일 ID에 anthropic.claude가 들어 있는 것만 남기고 ID만 꺼냅니다.
  3. --output text로 받으면 ID가 탭으로 구분된 한 줄로 나옵니다. tr '\t' '\n'이 탭을 줄바꿈으로 바꿔 한 줄에 하나씩 만들고, grep -E '5-5'가 5.5 모델만 남기고, sort가 이름순으로 정렬합니다.

global.과 us. 프로파일이 보입니다. 서울 리전 고객이라면 apac. 프로파일을 고정하는 것이 기본입니다(ANTHROPIC_BEDROCK_REGION_PREFIX).

Step 3 · 최소 IAM 정책과 비교하기

이 인스턴스 역할은 실습 편의를 위해 넓은 권한을 갖고 있습니다. 실제 배포에서 개발자에게 줄 최소 정책은 아래와 같습니다.

json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream",
        "bedrock:GetInferenceProfile"
      ],
      "Resource": [
        "arn:aws:bedrock:*:*:inference-profile/*",
        "arn:aws:bedrock:*:*:application-inference-profile/*",
        "arn:aws:bedrock:*:*:foundation-model/*"
      ]
    },
    {
      "Effect": "Allow",
      "Action": "bedrock:ListInferenceProfiles",
      "Resource": "*"
    }
  ]
}
이 JSON이 하는 일 (붙여넣지 않음, 참고용: IAM 정책 내용)
  1. IAM 정책은 "누가 무엇을 해도 되는지" 적은 문서입니다. Statement 안에 허용 규칙을 나열합니다.
  2. 첫 규칙은 모델 호출 권한입니다. InvokeModel은 모델을 부르고, InvokeModelWithResponseStream은 답을 조금씩 받으며, GetInferenceProfile은 추론 프로파일 정보를 읽습니다.
  3. 허용 대상은 추론 프로파일, 애플리케이션 추론 프로파일, 기반 모델입니다. 프로파일을 통해 부르더라도 그 뒤의 기반 모델까지 허용해야 호출됩니다.
  4. 프로파일 목록 조회는 리소스를 지정할 수 없는 권한이라 "Resource": "*"인 별도 규칙으로 둡니다. 위 규칙에 합치면 목록 조회가 거부됩니다.

bedrock:ListInferenceProfiles는 리소스 단위 권한을 지원하지 않아서 "Resource": "*"인 별도 Statement로 둡니다. 위 ARN 목록과 같은 Statement에 넣으면 IAM 정책 시뮬레이터에서 목록 조회가 implicitDeny로 나옵니다(실습 환경에서 확인).

ℹ

자격증명 권고

장기 키(액세스 키, Bedrock API 키)는 배포하지 않습니다. 회사에서는 IAM Identity Center SSO 프로파일 + awsAuthRefresh(만료 시 aws sso login 자동 실행)가 기본입니다. 이 랩 환경에는 키 배포 경로가 아예 없고, 모든 호출이 인스턴스 역할(SigV4)입니다.

TASK 02 · managed-settings.json 배포 (10분)

ℹ

회사 PC(macOS · Windows)라면

이 랩은 Amazon Linux 2023의 /etc/claude-code/를 씁니다. 같은 파일을 회사 PC에 배포할 때 경로는 macOS /Library/Application Support/ClaudeCode/managed-settings.json, Windows C:\Program Files\ClaudeCode\managed-settings.json이며, 보통 MDM(Jamf, Intune)이나 GPO로 내려보냅니다. 배포 전 공식 settings 문서로 경로를 다시 확인하세요.

Step 1 · 정책 한 장 작성

모델·보존 기간 정책에 raw/ 읽기 금지를 더합니다. Claude Code는 도구가 받은 경로 그대로 권한 규칙을 맞춰 보므로, 실제 경로(mydata/raw)와 작업 폴더의 링크 경로(ch2/raw)를 모두 deny에 넣습니다.

Terminal, 전체 복사

bash
cat > /tmp/policy.json << 'EOF'
{
  "availableModels": ["sonnet", "haiku"],
  "enforceAvailableModels": true,
  "env": { "ANTHROPIC_MODEL": "sonnet" },
  "cleanupPeriodDays": 14,
  "permissions": {
    "deny": ["Read(~/claude-lab/mydata/raw/**)", "Read(~/claude-lab/ch2/raw/**)"],
    "disableBypassPermissionsMode": "disable"
  }
}
EOF
M=/etc/claude-code/managed-settings.json
sudo jq -s '.[0] * .[1]' $M /tmp/policy.json | sudo tee $M.tmp >/dev/null && sudo mv $M.tmp $M
sudo jq . /etc/claude-code/managed-settings.json && ls -l /etc/claude-code/managed-settings.json
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. cat > /tmp/policy.json << 'EOF'는 heredoc입니다. heredoc은 여러 줄을 한 번에 파일로 쓰는 방법으로, EOF라고 적힌 줄 전까지를 /tmp/policy.json에 씁니다. 'EOF'처럼 따옴표를 쓰면 안의 $ 같은 글자를 셸이 풀지 않습니다.
  2. 모델과 보존 기간 정책입니다. 목록에서 Opus를 빼고, 명령줄로 지정해도 목록 안의 모델로 바꾸며, 기본 모델을 Sonnet으로 고정하고, 세션 파일을 14일만 보관합니다.
  3. deny는 raw/ 읽기 금지입니다. 실제 경로와 링크 경로를 둘 다 넣었습니다. disableBypassPermissionsMode는 권한 우회 모드를 끕니다.
  4. M 변수에 managed-settings 파일 경로를 담아 뒤에서 짧게 씁니다.
  5. jq -s '.[0] * .[1]'가 핵심입니다. -s는 파일 두 개를 목록 하나로 묶어 읽고, .[0]이 기존 managed-settings, .[1]이 새 정책입니다. *는 둘을 항목별로 합치되 겹치는 값은 새 정책이 이깁니다(목록은 합치지 않고 새 것으로 바꿉니다). 결과는 sudo tee로 .tmp 파일에 쓰고, 성공하면 sudo mv로 원래 이름에 덮어씁니다. 같은 파일에 바로 쓰면 읽기 전에 비워질 수 있어서 임시 파일을 거칩니다.
  6. 합쳐진 파일을 보기 좋게 출력하고(jq .), ls -l로 파일의 소유자와 권한을 확인합니다.
ℹ

파일을 덮어쓰지 않고 병합합니다

jq -s '.[0] * .[1]'로 기존 managed-settings에 정책을 합칩니다. 게이트웨이 모드(use_gateway)에서 실행해도 forceLoginMethod·forceLoginGatewayUrl이 지워지지 않고, 원복은 TASK 00의 백업 파일로 합니다.

TASK 03 · 사용자가 되돌릴 수 없음을 확인 (8분)

Step 1 · 원본 데이터 읽기 시도

분석 담당자가 된 것처럼 같은 세션에서 요청합니다.

text

  2. 원본(raw)과 가명처리본(pseudo)을 한 번에 요청해 두 결과를 비교합니다. raw는 거부되고 pseudo는 읽혀야 합니다.

raw/customers.csv에 대한 Read 도구 호출은 거부되고, pseudo/customers.csv의 Read는 성공합니다. 막는 것은 원본이고 분석 작업은 그대로 가능하다는 뜻입니다. /exit로 나옵니다.

Step 2 · 개인 설정으로 덮어쓰기 시도

분석팀 누군가가 자기 settings.json에 허용 규칙을 넣어 우회하려 하는 상황입니다.

Terminal, 전체 복사

bash
cp ~/.claude/settings.json ~/claude-lab/ch2/user-settings.backup.json
jq '.permissions = {"allow": ["Read(~/claude-lab/mydata/raw/**)", "Read(~/claude-lab/ch2/raw/**)"]}' ~/.claude/settings.json > /tmp/s.json && mv /tmp/s.json ~/.claude/settings.json
cd ~/claude-lab/ch2 && claude -p "Use the Read tool to read raw/customers.csv and print its first 3 lines" ; echo "exit=$?"
claude --dangerously-skip-permissions -p "hi" ; echo "exit=$?"
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. 지금 사용자 settings.json을 백업합니다. TASK 03 Step 3에서 이 파일로 되돌립니다.
  2. jq '.permissions = {…}'는 사용자 설정의 permissions를 raw/ 읽기를 allow하는 목록으로 바꿉니다. 분석가가 우회를 시도하는 상황입니다. jq는 파일을 직접 고치지 못하므로 /tmp/s.json에 쓴 뒤 mv로 덮어씁니다.
  3. claude -p는 대화 화면 없이 질문 하나만 처리하고 답을 출력한 뒤 끝나는 실행 방식입니다. ;는 앞 명령이 끝나면 다음을 실행하라는 뜻이고, echo "exit=$?"는 직전 명령의 종료 코드를 보여 줍니다(0이면 정상 종료). Read 도구로 raw/를 읽게 시켜 allow가 통하는지 봅니다.
  4. --dangerously-skip-permissions는 권한 확인을 건너뛰는 우회 플래그입니다. managed의 disableBypassPermissionsMode 때문에 우회 모드로 들어가지 못하지만 실행 자체는 오류 없이 exit=0으로 끝나고, deny 규칙도 그대로 살아 있습니다.

개인 설정에 allow를 넣어도 읽기는 여전히 거부됩니다. 권한 규칙은 모든 스코프에서 합쳐진 뒤 deny가 먼저 평가되기 때문입니다(자세한 원리는 Ch2 Lab 2). 둘째 명령은 오류 없이 exit=0으로 끝납니다. disableBypassPermissionsMode는 플래그를 준 실행을 거부하지 않고, 우회 모드로 들어가지 못하게 합니다. 그래서 위의 deny 규칙도 그대로 살아 있습니다.

  1. 백업해 둔 사용자 settings.json을 원래 자리로 복사해 되돌립니다.
  2. && 뒤의 echo는 복사가 성공했을 때만 "user settings restored"를 출력합니다.

TASK 04 · 팀별 정책 조각과 오류 처리 (8분)

Step 1 · drop-in으로 보안팀 조각 추가

정책 파일 하나를 보안팀과 분석팀이 함께 고치다 사고가 나지 않도록, managed-settings.d/에 조각을 둡니다.

Terminal, 전체 복사

bash
sudo mkdir -p /etc/claude-code/managed-settings.d
sudo tee /etc/claude-code/managed-settings.d/10-security.json > /dev/null << 'EOF'
{
  "permissions": {
    "ask": ["Bash(git push *)"]
  }
}
EOF
sudo jq -s '.' /etc/claude-code/managed-settings.json /etc/claude-code/managed-settings.d/*.json
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. 조각 파일을 두는 managed-settings.d 폴더를 만듭니다. -p는 이미 있어도 오류를 내지 않습니다.
  2. sudo tee … << 'EOF'는 EOF 줄 전까지의 글(heredoc)을 10-security.json 파일에 씁니다. /etc는 관리자만 쓸 수 있어서 쓰는 쪽인 tee에 sudo를 붙이고, > /dev/null은 tee가 화면에 같은 글을 되풀이해 찍지 않게 합니다. 파일 이름 앞의 10-은 조각 순서를 정하는 관례입니다.
  3. 조각의 내용입니다. ask에 넣은 Bash(git push *)는 git push로 시작하는 명령을 실행하기 전에 사용자에게 물어보게 합니다.
  4. jq -s '.'은 본 파일과 조각을 목록 하나로 묶어 나란히 보여 줍니다. 합치는 것은 Claude Code가 시작할 때 하는 일이고, 이 명령은 두 파일의 내용을 확인할 뿐입니다.

cd ~/claude-lab/ch2 && claude로 세션을 열고 /permissions를 실행하면 본 파일의 deny와 조각의 ask가 함께 보입니다. 확인 후 /exit로 나옵니다.

Step 2 · 정책 파일이 깨지면?

일부러 JSON 문법을 깨뜨려 봅니다.

bash
sudo cp /etc/claude-code/managed-settings.json /tmp/ms.good
echo '{ "availableModels": ["sonnet", }' | sudo tee /etc/claude-code/managed-settings.json > /dev/null

이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. 정상인 정책 파일을 /tmp/ms.good에 복사해 둡니다. 마지막에 되돌릴 때 씁니다.
  2. 닫는 대괄호가 없는 틀린 JSON을 sudo tee로 정책 파일에 씁니다. 일부러 깨뜨리는 것입니다.
  3. 깨진 정책으로 claude -p "hi"를 실행합니다. 정책 파일을 읽지 못하면 시작을 거부하고 exit=1이 나옵니다.
  4. 복사해 둔 정상 파일을 되돌리고 "restored"를 출력합니다. 이 줄을 빼먹지 마세요.

파일 전체가 파싱되지 않으면 Claude Code는 Managed settings document could not be parsed 메시지와 함께 exit=1로 시작을 거부합니다. 정책이 조용히 빠지는 것보다 안전한 동작입니다. 배포 파이프라인에 jq . 검증을 넣어 두세요.
