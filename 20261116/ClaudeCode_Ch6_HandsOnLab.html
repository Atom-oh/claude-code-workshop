Ch5까지 마치지 못했다면, 먼저 catchup

앞 랩이 중간에 실패했거나 건너뛰었다면, 실행 중인 claude를 모두 종료한 뒤 아래 한 줄로 이 랩을 시작할 수 있는 상태를 맞추고 TASK 00 블록을 실행합니다. 앞 랩을 마쳤다면 건너뜁니다.

bash
catchup ch6
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. catchup ch6는 남은 정책(managed-settings)을 ~/claude-lab/.catchup-backup/에 복사해 둔 뒤 비우고, 사용자 설정에서 Ch2 Lab 1의 raw 읽기 규칙과 Ch2 Lab 2의 permissions.ask·autoMode를 지우고(이전 파일은 settings.json.before-catchup으로 남김), 기본 모드(use_bedrock_direct)로 돌립니다. 이 랩의 작업 폴더 ~/claude-lab/ch6가 이미 있으면 지우지 않고 ~/claude-lab/.catchup-backup/으로 옮깁니다. 플러그인은 건드리지 않고, 채워 넣을 앞 랩 결과물도 없습니다. 게이트웨이 쪽 설정(예: TASK 03의 지출 한도)은 되돌리지 못하므로, 이전에 이 랩을 하다 멈췄다면 TASK 03 Step 4(원복)에서 bob의 1센트 한도를 지웠는지 확인합니다.

catchup: command not found가 나오면 아래 블록으로 같은 스크립트를 받아 실행합니다.

bash
bash <(curl -fsSL https://www.atomai.click/claude-code-workshop/20261116/assets/catchup.sh) ch6
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. curl -fsSL이 워크숍 사이트에서 catchup 스크립트를 받고(-f는 오류 페이지를 받지 않음, -s는 진행 표시를 숨기되 -S로 오류는 보여 주고, -L은 리디렉션을 따라감), bash <(…) ch6가 받은 스크립트를 ch6를 인자로 실행합니다. <( )는 명령의 출력을 파일처럼 넘기는 bash 문법이라, 스크립트 안의 sudo나 claude가 입력을 읽어도 스크립트가 중간에 끊기지 않습니다. 하는 일은 위 블록과 같습니다.

그림은 Preflight에서 본 키트 내려받기 전체입니다. 아래 블록의 3-4번째 줄은 그중 복사와 풀기만 하고, 이미 받았다면 아무것도 하지 않습니다.

Terminal, 전체 복사

bash
use_bedrock_direct >/dev/null
claude --version
KIT=${WS_KIT:-s3://ws-assets-prod-iad-r-iad-ed304a55c2ca1aee/5b8d0649-9ad2-43a8-8ff5-10ce7bb42e6f/mydata-kit.zip}
[ -d ~/claude-lab/mydata/pseudo ] || (aws s3 cp "$KIT" /tmp/mydata-kit.zip --only-show-errors && mkdir -p ~/claude-lab/mydata && unzip -qo /tmp/mydata-kit.zip -d ~/claude-lab/mydata)
sudo jq -e 'del(.forceLoginMethod, .forceLoginGatewayUrl) == {}' /etc/claude-code/managed-settings.json >/dev/null \
  && echo "정책 상태: 깨끗함" || echo "경고: 이전 챕터 정책이 남아 있습니다. catchup ch6을 실행한 뒤 이 블록을 다시 실행하세요"
rm -rf ~/claude-lab/ch6 2>/dev/null
mkdir -p ~/claude-lab/ch6 && cd ~/claude-lab/ch6
ln -sfn ~/claude-lab/mydata/pseudo pseudo
[ -d .git ] || git init -q
ls pseudo | head -4
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. use_bedrock_direct는 실습 환경에 준비된 명령으로, Claude Code를 Bedrock 직접 호출 모드로 맞춥니다. >/dev/null은 화면 출력을 버린다는 뜻입니다. claude --version은 설치된 버전을 보여 줍니다(기준은 2.1.290 이상).
  2. 키트가 있는 S3 주소를 KIT 변수에 담고, ~/claude-lab/mydata/pseudo 폴더가 없을 때만 내려받아 풉니다. [ -d … ] ||는 폴더가 있으면 뒤를 건너뛴다는 뜻이라, 이미 받았다면 아무 일도 하지 않습니다.
  3. managed-settings.json에서 forceLoginMethod, forceLoginGatewayUrl 두 키를 뺀 나머지가 빈 객체({})인지 jq -e로 확인합니다. 맞으면 "정책 상태: 깨끗함", 아니면 이전 챕터 정책이 남았다는 경고를 보여 줍니다. 줄 끝의 \는 명령이 다음 줄로 이어진다는 표시입니다.
  4. 이 챕터의 작업 폴더 ~/claude-lab/ch6를 rm -rf로 통째로 지우고 빈 폴더로 다시 만들어 들어갑니다. 다시 실행해도 같은 상태에서 시작하게 하려는 것입니다. ln -sfn은 가명 데이터 pseudo로 가는 바로가기(심볼릭 링크)를 걸고, [ -d .git ] ||는 git 저장소가 없을 때만 git init -q로 만듭니다.
  5. ls pseudo | head -4는 CSV 파일 이름 앞 네 개를 보여 줍니다. 이름이 보이면 준비가 끝난 것입니다.
ℹ

이 챕터는 빈 작업 폴더에서 시작합니다

Ch5의 ~/claude-lab/ch5와 다른 새 폴더 ~/claude-lab/ch6을 쓰므로 Ch5의 훅 설정(ch5/.claude/settings.json)이 적용되지 않습니다. 이번 챕터는 데이터를 분석하지 않고 게이트웨이 정책과 비용만 다루므로 가명 데이터 링크(pseudo)만 걸어 둡니다. ls에 CSV 파일 이름이 보이면 준비 완료입니다.

TASK 01 · 텔레메트리는 어디로 가는가

이 환경의 Claude Code는 OpenTelemetry로 사용량을 같은 PC의 Collector(127.0.0.1:4317, gRPC)에 보내고, Collector가 내 계정 CloudWatch와 워크샵 중앙 대시보드로 내보냅니다.

아래 그림은 사용량 데이터가 Claude Code에서 대시보드까지 가는 길입니다. 아래 블록은 그 길의 각 지점이 설정되어 있는지 확인합니다.

Terminal, 전체 복사

bash
jq '.env | with_entries(select(.key|test("TELEMETRY|OTEL_")))' ~/.claude/settings.json
systemctl is-active otelcol.service cco-central-fanout.timer
sudo grep -n -A4 'scrub_logs:' /etc/otelcol/config.yaml
sudo grep -n 'exporters: \[' /etc/otelcol/config.yaml
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. ~/.claude/settings.json의 env 항목 가운데 키 이름에 TELEMETRY 또는 OTEL_이 들어간 것만 골라 보여 줍니다. test("…|…")는 정규식 검사이고, with_entries(select(…))는 조건에 맞는 항목만 남깁니다. OTEL_RESOURCE_ATTRIBUTES의 user.email, team.id를 찾아봅니다.
  2. systemctl is-active는 서비스 상태를 한 단어로 보여 줍니다. otelcol.service와 cco-central-fanout.timer 둘 다 active가 나와야 합니다.
  3. Collector 설정 파일에서 scrub_logs:가 있는 줄 번호(-n)와 그 뒤 4줄(-A4)을 보여 줍니다. 이 설정이 이벤트 로그에서 프롬프트 본문을 삭제합니다. 설정 파일은 관리자만 읽을 수 있어 sudo를 씁니다.
  4. exporters: [가 있는 줄을 찾아 파이프라인별로 어디로 내보내는지 보여 줍니다. 목록에 clickhouse가 보이면 중앙 대시보드로도 이중 전송 중입니다.

읽어 볼 포인트입니다.

  • OTEL_RESOURCE_ATTRIBUTES의 user.email, team.id가 대시보드에서 사람·팀별로 묶는 키입니다. 회사에서는 사번이나 부서 코드를 넣습니다.
  • scrub_logs가 이벤트 로그에서 프롬프트 본문을 삭제한 뒤 내보냅니다. 비용은 보되 내용은 남기지 않는 DLP 설정입니다.
  • exporters에 clickhouse가 보이면 중앙 대시보드로도 이중 전송 중입니다.
ℹ

강사 화면: 사용량 대시보드

강사가 중앙 대시보드에서 지금까지의 모든 참가자 세션(모델, 토큰, 컨텍스트 사용량, CLAUDE.md/MCP 수)을 보여 줍니다. 자연어 챗봇에 "지난 1시간 동안 토큰을 가장 많이 쓴 팀은?"처럼 물어보는 것도 시연합니다. 주요 지표는 claude_code.token.usage, claude_code.cost.usage이고, 플러그인 사용 현황은 plugin_loaded 이벤트로 봅니다.

TASK 02 · Apps Gateway 로그인과 그룹별 모델 정책

Ch2 Lab 1 TASK 06에서 bob으로 그룹 모델 정책을 봤습니다. 이번에는 자산분석팀의 alice와 타 부서의 bob을 비교하고 지출 한도까지 다룹니다. 같은 VPC의 Claude Apps Gateway를 거치도록 바꿉니다. 게이트웨이는 사내 IdP(이 랩에서는 Cognito)로 사용자를 식별하고, 그룹별로 모델과 지출 한도를 적용한 뒤 Bedrock을 대신 호출합니다.

계정 소속 그룹 허용 모델 일일 한도
alice@workshop.example 자산분석팀 (상위 모델 허용) power-users Opus, Sonnet, Haiku 5.5 $200
bob@workshop.example 타 부서 (제한) standard-users Sonnet, Haiku 5.5 $50

비밀번호는 팀 페이지 Outputs 표의 GatewayDemoPassword 값입니다(기본 DemoPassword123!).

아래 그림은 TASK 02의 로그인과 그룹 정책, TASK 03의 지출 한도까지 이어지는 전체 흐름입니다. 게이트웨이는 사용자를 식별한 뒤 그룹 정책으로 요청을 허용하거나 막고, 허용한 요청만 Bedrock으로 보냅니다.

Step 1 · 게이트웨이가 보이는지 확인

Terminal, 전체 복사

bash
GW=https://gateway.workshop.internal
dig +short gateway.workshop.internal
curl -ks $GW/.well-known/oauth-authorization-server | jq .issuer
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. 게이트웨이 주소를 GW 변수에 담고, dig +short로 그 이름이 어떤 IP로 풀리는지 한 줄로 봅니다. 사설 IP 하나가 나와야 합니다. 게이트웨이는 VPC 안에서만 열려 있습니다.
  2. curl로 게이트웨이의 /.well-known/oauth-authorization-server(로그인에 쓰는 인증 서버 정보 문서)를 받아 jq .issuer로 issuer URL만 꺼냅니다. -k는 자체 서명 인증서 검사를 건너뛰고 -s는 진행 표시를 숨깁니다. 랩 게이트웨이가 자체 서명 인증서를 쓰기 때문입니다.

사설 IP 하나와 issuer URL이 나오면 정상입니다. 게이트웨이는 VPC 안에서만 열려 있어 인터넷에서는 닿지 않습니다.

Step 2 · 게이트웨이 모드로 전환

bash
use_gateway
sudo jq . /etc/claude-code/managed-settings.json
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. use_gateway는 실습 환경에 준비된 명령으로, 이 PC의 Claude Code를 게이트웨이 모드로 바꿉니다.
  2. managed-settings.json을 보기 좋게 출력합니다. forceLoginMethod: "gateway"와 forceLoginGatewayUrl이 들어 있어야 합니다. managed 설정은 사용자가 바꿀 수 없어서, 이 PC는 게이트웨이 로그인 없이는 쓸 수 없습니다.

managed settings에 forceLoginMethod: "gateway"와 forceLoginGatewayUrl이 들어갔습니다. 사용자는 이 설정을 바꿀 수 없으므로, 이 PC의 Claude Code는 이제 게이트웨이 로그인 없이는 쓸 수 없습니다(Ch2 Lab 1의 정책 배포와 같은 원리).

Step 3 · alice로 로그인

bash
cd ~/claude-lab/ch6 && claude
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. 작업 폴더에서 Claude Code를 엽니다. 처음 여는 폴더라 Accessing workspace 창이 먼저 뜨면 ↓로 Yes, I trust this folder를 고르고 Enter를 누릅니다. 로그인 화면이 뜨면 alice@workshop.example(비밀번호 DemoPassword123!, 팀 Outputs의 GatewayDemoPassword)로 로그인합니다.
  1. 로그인 화면이 뜨면 안내를 따릅니다. 세션 안이라면 /login을 입력합니다.
  2. 신뢰하지 않는 게이트웨이 경고가 나오면 Yes, trust this gateway를 고릅니다. 랩 게이트웨이가 자체 서명 인증서를 쓰기 때문입니다.
  3. 터미널에 표시된 URL을 브라우저에서 열고 코드를 확인한 뒤 alice@workshop.example(비밀번호 DemoPassword123!, 팀 Outputs의 GatewayDemoPassword)로 로그인합니다.
  4. 터미널로 돌아와 로그인 완료를 확인합니다.

로그인하기 전에는 시작 화면과 상태줄에 Opus 4.7 · Cloud gateway처럼 게이트웨이와 무관한 기본 모델 이름이 보일 수 있습니다. 로그인하면 Claude Code가 조직 설정을 받으려고 스스로 다시 시작하고, Using … 5.5 (from managed settings) 줄과 함께 게이트웨이가 그룹별로 정한 5.5 모델로 바뀝니다.

text
/status
이 입력이 하는 일 (붙여넣는 곳: Claude 입력창)
  1. /status는 지금 연결 방식을 보여 줍니다. API provider가 Cloud gateway, Gateway URL이 https://gateway.workshop.internal이어야 합니다. 로그인한 계정의 이메일은 여기에 나오지 않으므로, alice인지 bob인지는 다음 /model 목록(alice만 Opus가 있음)으로 구분합니다. Esc로 닫습니다.
text
/model
이 입력이 하는 일 (붙여넣는 곳: Claude 입력창)
  1. /model은 고를 수 있는 모델 목록을 보여 줍니다. alice는 Opus, Sonnet, Haiku 5.5가 모두 보이고, 이 목록은 게이트웨이가 그룹 정책으로 내려준 것입니다. bob으로 로그인했을 때는 Opus가 없는지 확인합니다.

Opus, Sonnet, Haiku 5.5가 모두 보입니다. 이 목록은 내 settings.json이 아니라 게이트웨이가 그룹 정책으로 내려준 것입니다. 간단한 질문을 하나 보낸 뒤 /usage에서 Spend limit 막대를 확인합니다.

text
/usage
이 입력이 하는 일 (붙여넣는 곳: Claude 입력창)
  1. /usage에서 Spend limit 막대(오늘 쓴 금액이 한도의 몇 %인지)를 확인합니다. 질문을 하나 보낸 뒤에 열어야 사용 기록이 반영됩니다.

Step 4 · bob으로 바꿔 로그인

text
/logout
이 입력이 하는 일 (붙여넣는 곳: Claude 입력창)
  1. 현재 계정에서 로그아웃합니다. 로그아웃하면 Claude Code가 끝나고 터미널로 돌아옵니다.

Claude Code의 로그인은 지워졌지만, 승인 페이지를 연 브라우저에는 alice의 로그인이 남아 있습니다. 그대로 두면 다음 승인 때 비밀번호를 묻지 않고 alice로 다시 들어갑니다. 그래서 bob은 alice의 로그인이 없는 시크릿 창에서 승인합니다. 먼저 터미널에서 게이트웨이 로그인을 한 번 더 지웁니다.

bash
gateway_logout
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. 실습 환경에 준비된 명령입니다. Claude Code의 게이트웨이 로그인을 한 번 더 지우고, 브라우저에 남은 로그인을 지우는 로그아웃 주소(https://….auth.us-east-1.amazoncognito.com/logout?…)를 출력합니다.

TASK 03 · 관리자가 되어 지출 한도 걸기

두 번째 터미널을 열어(code-server 터미널 패널의 +) 관리자 역할을 합니다. 게이트웨이 Admin API는 VPC 안에서만 열려 있고, 이 랩의 키는 고정값입니다.

Step 1 · 현재 적용 한도 조회

Terminal 2, 전체 복사

bash
GW=https://gateway.workshop.internal
READ=claude-gateway-admin-read-secret; WRITE=claude-gateway-admin-write-secret
curl -ks "$GW/v1/organizations/spend_limits/effective?period[]=daily&q=bob" -H "x-api-key: $READ" | tee /tmp/eff.json | jq .
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. 게이트웨이 주소를 GW 변수에 담습니다. 이 블록은 두 번째 터미널(관리자 역할)에서 실행합니다.
  2. Admin API 키를 변수에 담습니다. READ는 조회용, WRITE는 한도를 바꾸는 쓰기용입니다. 한 줄에 둘을 ;로 이어 썼습니다. 이 키는 폐기되는 실습 계정 전용 고정값입니다.
  3. curl로 bob에게 지금 적용되는 하루(daily) 한도를 조회합니다. q=bob은 사용자를 bob으로 좁히는 검색어이고, -H "x-api-key: …"로 키를 보냅니다. tee /tmp/eff.json은 응답을 파일에 저장하면서 화면 쪽으로도 넘기고, jq .가 보기 좋게 출력합니다.
ℹ

Admin 키가 페이지에 그대로 있는 이유

이 키는 폐기되는 실습 계정 전용 고정값입니다. 운영에서는 Secrets Manager 같은 비밀 저장소에 두고 주기적으로 교체하며, write 키는 소수의 관리자만 갖게 합니다.

bob의 항목(.data[0])에서 세 가지를 봅니다.

bash
jq '.data[0] | {user_id: .scope.user_id, amount, source, period_to_date_spend}' /tmp/eff.json
BOB=$(jq -r '.data[0].scope.user_id' /tmp/eff.json); echo "BOB=$BOB"
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. 저장한 응답의 첫 항목(.data[0])에서 사용자 ID, 한도 금액(amount, 센트), 그 출처(source), 오늘 쓴 금액(period_to_date_spend)만 골라 보여 줍니다. amount와 source가 둘 다 null이면 한도가 없는 상태입니다.
  2. jq -r로 사용자 ID를 따옴표 없는 글자로 꺼내 BOB 변수에 담고 확인용으로 출력합니다. $( … )는 안의 명령 결과를 값으로 쓴다는 뜻입니다. BOB=가 비어 있으면 bob 세션에서 질문을 더 보낸 뒤 다시 조회합니다.
필드 의미
scope.user_id Cognito의 사용자 고유 ID. 한도를 걸 때 씁니다
amount, source 지금 bob에게 적용되는 한도(US 센트)와 그 출처(그룹 등). 둘 다 null이면 한도가 없는 상태입니다
period_to_date_spend 오늘 bob이 쓴 금액(US 센트, 문자열)

지출 기록이 있는 사용자만 나오므로, BOB=가 비어 있다면 bob 세션에서 질문을 하나 더 보낸 뒤 다시 조회합니다.

Step 2 · bob에게만 1센트 한도

bash
curl -ks -X POST $GW/v1/organizations/spend_limits -H "x-api-key: $WRITE" \
  -H 'Content-Type: application/json' \
  -d "{\"scope\":{\"type\":\"user\",\"user_id\":\"$BOB\"},\"amount\":\"1\",\"period\":\"daily\"}" | tee /tmp/lim.json | jq .
LIMIT_ID=$(jq -r .id /tmp/lim.json); echo "LIMIT_ID=$LIMIT_ID"
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. curl -X POST로 새 한도를 만듭니다. 쓰기 키(WRITE)로 인증하고, 본문(-d)은 JSON입니다. scope는 type: user와 bob의 user_id(\"는 큰따옴표 안에 큰따옴표를 넣는 표기), amount: "1"은 1센트(US 센트 단위 문자열), period: daily는 하루 단위입니다. 줄 끝의 \는 한 명령을 여러 줄로 이은 표시이고, tee는 응답을 /tmp/lim.json에 저장합니다.
  2. 응답의 id(spl_… 모양)를 LIMIT_ID에 담습니다. TASK 03 Step 4에서 이 한도를 지울 때 필요합니다.

LIMIT_ID는 spl_… 형태입니다. amount는 US 센트 단위 문자열이고, 사용자 한도는 그룹 한도보다 우선합니다.

Step 3 · bob 세션에서 확인

첫 번째 터미널의 bob 세션에서 질문을 하나 더 보냅니다. 지출 집계가 반영되는 데 약간 걸릴 수 있으니, 바로 막히지 않으면 질문을 1~2개 더 보내 보세요.

text
pseudo 디렉터리에 파일이 몇 개 있는지 알려줘
이 입력이 하는 일 (붙여넣는 곳: Claude 입력창)
  1. 첫 번째 터미널의 bob 세션에서 질문을 보냅니다. 오늘 쓴 금액이 1센트 한도보다 크므로 "spend limit reached" 메시지로 거절되어야 합니다. 바로 막히지 않으면 질문을 1~2개 더 보냅니다.

요청이 spend limit reached (daily; resets … UTC)와 "You have reached your spend limit. Contact your administrator to request an increase." 메시지로 거절됩니다. /usage를 열면 Spend limit 막대가 100%를 넘어(예: 823% used, $0.08 / $0.01) 표시됩니다. 오늘 이미 쓴 금액이 새 한도보다 크기 때문입니다. Esc로 닫습니다. 회사에서는 이 메시지에 사내 증액 요청 절차를 적어 둡니다.

ℹ

한도가 동작하는 방식

한도에 가까워지면 75%, 95%에서 경고가 먼저 나오고, 넘으면 다음 요청부터 막힙니다. 이미 진행 중인 응답은 끝까지 갑니다. 한도 저장소에 문제가 생겼을 때 기본 동작은 차단이 아닌 통과(fail-open)이므로, 운영에서는 이 선택을 명시적으로 정해 두세요.

Step 4 · 원복

Terminal 2

bash
curl -ks -X DELETE $GW/v1/organizations/spend_limits/$LIMIT_ID -H "x-api-key: $WRITE" -o /dev/null -w 'delete=%{http_code}\n'
curl -ks "$GW/v1/organizations/spend_limits/effective?period[]=daily&q=bob" -H "x-api-key: $READ" | jq -c '.data[0] | {amount, source, period_to_date_spend}'
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. curl -X DELETE로 방금 만든 한도(LIMIT_ID)를 지웁니다. -o /dev/null은 응답 본문을 버리고, -w 'delete=%{http_code}\n'은 결과 코드만 출력합니다. delete=200이 나와야 합니다.
  2. Step 1과 같은 조회를 다시 하되 amount, source, period_to_date_spend만 한 줄로 봅니다(jq -c). amount와 source가 Step 1과 같아졌으면 원복된 것입니다.

delete=200이 나오고 bob의 amount·source가 Step 1과 같아진 것(그룹 한도 또는 null)을 확인하고, bob 세션에서 질문이 다시 통과하는지 봅니다. 마지막으로 첫 번째 터미널에서 /exit 후 기본 모드로 돌아갑니다.

bash
use_bedrock_direct
sudo jq . /etc/claude-code/managed-settings.json
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. use_bedrock_direct로 기본 모드(Bedrock 직접 호출)로 돌아옵니다. 첫 번째 터미널에서 /exit로 나온 뒤 실행합니다.
  2. managed-settings.json을 출력해 forceLoginMethod가 없는지 확인합니다.

선택 TASK 04 · 계약 단가로 비용 표시하기

/usage와 OTel의 비용은 목록가 기준 추정치입니다. 조직의 할인율을 반영해 보여 주려면 managed settings의 modelPricing을 씁니다. 기본 모드(use_bedrock_direct)에서 진행합니다.

Terminal, 전체 복사

bash
M=/etc/claude-code/managed-settings.json
sudo cp $M ~/claude-lab/ch6/managed-settings.backup.json
echo '{ "modelPricing": { "multiplier": 0.9 } }' > /tmp/policy.json
sudo jq -s '.[0] * .[1]' $M /tmp/policy.json | sudo tee $M.tmp >/dev/null && sudo mv $M.tmp $M
sudo jq . $M
cd ~/claude-lab/ch6 && claude
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. 정책 파일 경로를 M 변수에 담고, 바꾸기 전 모습을 managed-settings.backup.json으로 복사해 둡니다. 원복할 때 쓰는 백업입니다.
  2. 새로 넣을 정책 조각 { "modelPricing": { "multiplier": 0.9 } }를 임시 파일에 씁니다. multiplier는 목록가에 곱하는 배율이고, 0.9는 계약 단가가 목록가의 90%라는 가정입니다.
  3. jq -s '.[0] * .[1]'가 정책 파일과 새 조각을 합칩니다(-s는 두 파일을 배열로 묶고, *는 객체 합치기). 합친 결과를 sudo tee $M.tmp로 임시 파일에 쓰고, 성공하면 mv로 원래 파일을 바꿉니다. 쓰기에 관리자 권한이 필요해 sudo를 씁니다.
  4. 결과를 출력해 modelPricing이 들어갔는지 확인하고, 작업 폴더에서 Claude Code를 엽니다. 질문을 하나 보낸 뒤 /usage에서 비용 줄의 표시를 봅니다.

질문을 하나 보낸 뒤 /usage에서 비용 줄에 조직 설정 단가(configured rates) 기준이라는 표시가 붙는지 확인합니다. 표시가 다르면 배포된 버전의 공식 문서를 기준으로 진행자와 확인합니다.

⚠

정산은 AWS 청구서가 기준입니다

modelPricing은 화면과 텔레메트리의 추정치를 계약 단가에 가깝게 보정할 뿐입니다. 실제 비용은 Cost Explorer와 대사하세요.

원복

bash
sudo cp ~/claude-lab/ch6/managed-settings.backup.json /etc/claude-code/managed-settings.json && sudo jq . /etc/claude-code/managed-settings.json
이 블록이 하는 일 (붙여넣는 곳: 터미널)
  1. 백업해 둔 파일로 managed-settings.json을 되돌리고(cp) 결과를 출력해 modelPricing이 사라졌는지 확인합니다. &&라 복사에 성공했을 때만 출력합니다.
