R2-1 정기 분석 리포트: 설치한 plugin으로 같은 형식의 리포트를 반복해서 만들기

R2 공통 단계에서 설치한 plugin의 skill과 agent만으로 정해진 형식의 분석 리포트를 두 번 만들고, 그동안 agent와 skill을 하나도 새로 짜지 않았음을 확인한다

정기 리포트의 핵심은 매번 같은 절차, 같은 형식입니다. 그 절차와 형식은 이미 periodic-report skill에 들어 있습니다. 이 미션에서는 동료 폴더 ~/claude-lab/capstone-try/에서 /my-kit:periodic-report를 대상이나 기간만 바꿔 두 번 돌리고, 결과의 형식이 같은지, 쓴 agent와 skill이 모두 plugin에서 왔는지 봅니다. R2 공통 단계를 먼저 끝내야 합니다.

plugin의 skill을 명령으로 불러 첫 정기 리포트를 reports/에 만듭니다.

왜 필요한가요: 절차와 형식은 이미 skill(절차와 출력 형식을 적은 SKILL.md)에 있어서, 요청에는 대상과 기간만 줍니다. 아래 그림은 명령 한 줄 뒤에 plugin 안에서 일이 어떻게 넘어가는지 보여 줍니다.

skill의 출력 형식대로 요약, 핵심 표, 눈에 띄는 변화와 이유, 확인하지 못한 것, 검토 결과의 다섯 항목이 그 순서로 있어야 합니다. 형식이 다르면 skill을 고치지 말고 세션에서 "periodic-report의 출력 형식 그대로 다시 정리해 주세요"라고 요청합니다.

reports/에는 같은 이름의 .html도 있습니다. skill의 웹 리포트 형식대로 만든 한 장짜리 보고서입니다. code-server 편집기는 HTML을 그림으로 보여 주지 않으므로, 폴더를 작은 웹 서버로 띄워 브라우저 탭에서 엽니다.

Terminal 2, 웹 리포트 열기
cd ~/claude-lab/capstone-try
grep -cHE 'src="https?://|href="https?://' reports/*.html
python3 -m http.server 8000

둘째 줄은 리포트마다 외부 주소 개수를 셉니다. 줄 끝의 숫자가 모두 0이면 파일 하나로 완결된 것입니다. 셋째 줄이 Serving HTTP on 0.0.0.0 port 8000을 내면 오른쪽 아래 Your application running on port 8000 is available. 알림의 Open in Browser를 누르고, 새 탭에서 reports/ 안의 .html을 누릅니다. 알림을 놓쳤다면 IDE 주소의 도메인 뒤에 /proxy/8000/reports/를 붙여 엽니다(예: https://…cloudfront.net/proxy/8000/reports/). 요약 박스, KPI 카드, 막대 차트, 핵심 표가 보이면 됩니다(예시는 Ch4 TASK 04 Step 4의 그림). 다 봤으면 Ctrl C로 서버를 끕니다.

가드레일에 막히면 리포트를 만드는 도중에 DLP:, KEY:, NET:, MCP:로 시작하는 메시지가 나오면 가드레일이 제 일을 한 것입니다. 우회하지 말고, 어떤 요청이 막혔는지 화면을 남겨 두면 출품 양식 4번에 쓸 수 있습니다.

같은 형식으로 한 번 더

10분

대상이나 기간만 바꿔 같은 명령을 다시 보내고, 두 리포트의 형식이 같은지 봅니다.

왜 필요한가요: 입력만 바꿔 두 번 돌렸는데 형식이 같아야, 그 형식이 프롬프트가 아니라 skill에서 왔다고 말할 수 있습니다.

01 표의 두 번째 칸을 보냅니다. 같은 세션이어도 되고 새 세션이어도 됩니다. 같은 대상의 지난 리포트가 있으면 skill의 절차대로 "눈에 띄는 변화와 이유"에서 지난 리포트와 비교합니다(트랙 B 강남구 202609와 202610, 트랙 C alphavantage 9월과 10월).

끝나면 01의 첫 번째 Terminal 2 블록(제목 줄 보기)을 다시 실행해 두 파일의 제목 줄이 같은 다섯 항목인지 봅니다. 프롬프트로 형식을 길게 설명하지 않았는데도 형식이 같다면, 형식은 프롬프트가 아니라 skill에서 왔다는 뜻입니다.

정기 실행으로 넓히려면 매주 같은 시각에 돌리는 일은 이번 미션의 범위 밖입니다. 이 skill은 명령 한 줄로 불리므로, 나중에 같은 명령을 정해 둔 일정으로 실행하게 해도 결과의 형식은 그대로입니다.

03

재사용 확인

10분

두 리포트를 만드는 동안 agent와 skill을 하나도 새로 짜지 않았고, 쓴 것이 모두 설치한 plugin에서 왔음을 보입니다.

왜 필요한가요: 이 미션의 핵심은 "새로 짜지 않고 설치한 plugin으로" 해 냈다는 것입니다. 지문 검사가 그 기준이고, 세션의 답은 보조 증거입니다.

Terminal 2, 전체 복사
cd ~/claude-lab/capstone-try && . ~/claude-lab/capstone/r2.env
(cd ~/claude-lab/capstone/marketplace/plugins/$KIT && sha256sum -c ~/claude-lab/capstone-try/kit.sha)
find . -path ./.git -prune -o \( -path '*/agents/*' -o -name SKILL.md \) -print
ls -lt ~/.claude/agents ~/.claude/skills 2>/dev/null
claude plugin details $KIT@capstone-local | grep -E 'Skills|Agents|Hooks|MCP servers'

네 가지를 봅니다. sha256sum -c가 모두 OK면 설치 뒤에 plugin의 agent와 skill이 바뀌지 않았습니다. find가 아무것도 출력하지 않으면 이 폴더에 따로 만든 agent나 skill이 없습니다. ls -lt ~/.claude/agents ~/.claude/skills는 사용자 수준의 agent와 skill입니다. 앞선 실습에서 만든 것이 보여도 이 미션의 "새로 짠 것"으로 세지 않습니다. 이름에 my-kit:이 붙지 않아 세션 답에서도 구분됩니다. 다만 날짜가 오늘 R2 시간대인 파일이 있으면 그것은 이번 업무를 위해 새로 짠 것이니 지우거나 plugin으로 옮깁니다. claude plugin details의 수는 R2 공통 04에서 본 것과 같아야 합니다.

세션에서도 물어봅니다.

Claude 세션 입력
이번 세션에서 쓴 skill과 subagent의 이름을 모두 적고, 각각 어디서 왔는지(plugin 이름, 또는 이 폴더) 알려 주세요.

답에 my-kit:periodic-report와 my-kit:이 붙은 agent만 나오면 됩니다. 이 답은 모델의 설명이라 보조 증거이고, 지문 검사가 기준입니다.

skill을 고치고 싶어졌다면 두 번 돌려 보니 형식을 바꾸고 싶을 수 있습니다. 그때는 이 폴더에 새 skill을 만들지 말고, ~/claude-lab/capstone/my-kit/ 원본을 고친 뒤 버전을 올리고 R2 공통 03으로 다시 배포합니다. 그다음 R2 공통 04의 4번 블록으로 kit.sha를 다시 만들고, 바꾼 내용을 출품에 적습니다. 업무마다 agent와 skill을 새로 짜는 것이 아니라, 하나의 plugin을 고쳐 가며 쓰는 것이 재사용입니다.

04

정리

5분

리포트에 개인정보 패턴과 키가 없는지 보고, 출품에 쓸 메모를 남깁니다.

왜 필요한가요: 리포트와 메모는 출품 때 다른 사람에게 보입니다. 올리기 전에 개인정보 패턴과 키가 없는지 확인합니다.

Terminal 2, 전체 복사
cd ~/claude-lab/capstone-try
grep -nE '(^|[^0-9])([0-9]{6}-[1-4][0-9]{6}|[0-9]{4}-[0-9]{4}-[0-9]{4}-[0-9]{4}|01[016789]-[0-9]{3,4}-[0-9]{4})([^0-9]|$)' reports/*.md reports/*.html || echo "개인정보 패턴 없음"
jq -r '.. | objects | (.SEOUL_API_KEY?, .ALPHA_VANTAGE_API_KEY?, .Authorization?) | strings | sub("^Bearer "; "")' ~/.claude.json 2>/dev/null \
  | while IFS= read -r V; do [ ${#V} -ge 8 ] && grep -rlF -- "$V" reports/ ; done
echo "키 검사 끝 (위에 파일 이름이 나오면 그 파일에 키나 토큰이 있습니다)"

개인정보 패턴 없음과 키 검사 끝 사이에 파일 이름이 없으면 됩니다. 키 검사는 R1에서 read -rs로 받아 ~/.claude.json에 등록한 값만 찾습니다. 설치 창(userConfig)에만 넣은 키는 비밀 저장소에 있어 찾지 못하니, 그 키를 붙여 넣은 적이 없는지 스스로도 확인합니다. 아래는 트랙 B의 메모 예입니다. 내 트랙에 맞게 바꿔 둡니다.

출품 메모, 예시
[R2-1 정기 분석 리포트]
plugin: my-kit 0.1.0 (트랙 B), 설치: /plugin install my-kit@capstone-local
같은 형식으로 두 번: reports/202609-강남구.md, reports/202610-강남구.md
쓴 것: /my-kit:periodic-report, my-kit:price-summarizer, my-kit:anomaly-checker (새로 짠 agent, skill 없음, kit.sha 모두 OK)

(선택) 웹 리포트를 공개 주소로 공유. 01의 /proxy/8000 주소는 내 code-server 로그인이 있어야 열리므로 다른 사람에게 보낼 수 없습니다. 쇼케이스에서 다른 사람이 열게 하려면, 검사를 통과한 .html만 따로 모아 정적 파일의 표준 배포 패턴인 비공개 S3 + CloudFront(OAC) + BucketDeployment로 올립니다. 링크를 아는 누구나 열 수 있는 주소입니다. 트랙 C의 github와 docs처럼 회사 저장소나 내부 문서 내용이 담긴 리포트는 이 단계를 건너뜁니다. 필수 단계가 아니고, 시간이 남을 때만 합니다.

Terminal 2, 올릴 파일만 모으기
S=~/claude-lab/r21-share/site
rm -rf "$S" && mkdir -p "$S" && cd ~/claude-lab/capstone-try
for f in reports/*.html; do
  if grep -qE '(^|[^0-9])([0-9]{6}-[1-4][0-9]{6}|[0-9]{4}-[0-9]{4}-[0-9]{4}-[0-9]{4}|01[016789]-[0-9]{3,4}-[0-9]{4})([^0-9]|$)' "$f"; then echo "건너뜀(개인정보 패턴): $f"; else cp "$f" "$S/"; fi
done
jq -r '.. | objects | (.SEOUL_API_KEY?, .ALPHA_VANTAGE_API_KEY?, .Authorization?) | strings | sub("^Bearer "; "")' ~/.claude.json 2>/dev/null \
  | while IFS= read -r V; do [ ${#V} -ge 8 ] && grep -rlF -- "$V" "$S" | while IFS= read -r K; do echo "지움(키 포함): $K"; rm -f "$K"; done; done
echo "올릴 파일:"; ls "$S"

블록은 올릴 폴더 ~/claude-lab/r21-share/site를 매번 비우고 새로 만듭니다. 개인정보 패턴이 있는 리포트는 건너뜀으로 알리고 복사하지 않습니다. R1에서 등록한 키가 든 리포트는 지움(키 포함)으로 알리고 site/에서 지웁니다. 건너뛰거나 지운 리포트를 올리고 싶으면 리포트를 고친 뒤 이 블록을 다시 실행합니다. 올릴 파일: 아래에 보이는 .html만 올라갑니다. 원본 .md, kit.sha, 설정 파일은 올라가지 않습니다.

배포 코드는 capstone-try 밖의 ~/claude-lab/r21-share에 둡니다. 03의 지문 검사를 하는 폴더를 깨끗하게 두기 위해서입니다. 그 폴더에서 Claude를 새로 열고 배포를 맡깁니다.

Terminal
cd ~/claude-lab/r21-share && claude
Claude 세션 입력
site/ 폴더의 html만 공개하는 CDK 스택을 infra/에 TypeScript로 만들고 배포해 주세요.
- S3 버킷은 퍼블릭 접근을 모두 막고, CloudFront는 OAC로만 버킷을 읽는다
- BucketDeployment로 site/ 안의 파일만 버킷 맨 위에 올린다. 다른 폴더와 파일은 올리지 않는다
- 리전은 환경 변수 AWS_REGION의 값(실습 리전). 스택 이름 R21ReportShare, removalPolicy DESTROY + autoDeleteObjects
- 출력 이름은 정확히 ShareUrl(https://로 시작하고 끝에 /가 없는 CloudFront 주소)과 BucketName
- 이 계정과 리전에 CDK bootstrap이 안 되어 있으면 bootstrap부터 한다
- 주소 확인은 내가 다른 터미널에서 하니, 배포가 끝나면 출력 값만 알려 준다

코드 작성과 bootstrap까지 10~15분 걸립니다. 도구 사용 허락을 물으면 명령을 읽고 허락합니다. Claude가 주소를 직접 열어 보려다 NET:으로 막히면 가드레일이 제 일을 한 것이니, 확인은 아래 블록으로 두 번째 터미널에서 합니다.

Terminal 2, 전체 복사
R=${AWS_REGION:-$(aws configure get region)}; cd ~/claude-lab/r21-share
out() { aws cloudformation describe-stacks --region "$R" --stack-name R21ReportShare --query "Stacks[0].Outputs[?OutputKey=='$1'].OutputValue" --output text; }
U=$(out ShareUrl); B=$(out BucketName); echo "$U"
for f in site/*.html; do
  P=$(python3 -c 'import sys, urllib.parse; print(urllib.parse.quote(sys.argv[1]))' "$(basename "$f")")
  echo "$(curl -s -o /dev/null -w '%{http_code}' "$U/$P") CloudFront  $(curl -s -o /dev/null -w '%{http_code}' "https://$B.s3.$R.amazonaws.com/$P") S3 직접  $f"
done

리포트마다 200 CloudFront와 403 S3 직접이 함께 나오면 됩니다. 버킷은 잠겨 있고, 들어오는 길은 CloudFront 하나뿐이라는 뜻입니다. 첫 줄의 주소 뒤에 파일 이름을 붙여 브라우저에서 열어 보고, 그 주소를 쇼케이스 스레드나 출품 메모에 붙입니다. 파일 이름이 한글이면 브라우저 주소창에 그대로 붙여도 열립니다.

첫 줄이 비어 있고 모든 줄이 000이면 출력 이름이 다른 것입니다. Claude에게 "출력 이름을 ShareUrl과 BucketName으로 바꿔 다시 배포해 주세요"라고 요청합니다. CloudFront가 계속 403이면 파일이 버킷 맨 위가 아닌 곳에 올라간 것일 수 있으니 aws s3 ls "s3://$B/" --recursive로 객체 이름을 봅니다.

쇼케이스가 끝나면 내립니다 공개 주소는 켜 둔 동안 누구나 열 수 있습니다. 쇼케이스가 끝나면 cd ~/claude-lab/r21-share/infra && npx aws-cdk@2 destroy --force로 스택과 버킷을 함께 지웁니다. 다른 배포 패턴(서버 앱, API)은 Capstone Setup의 출품 방법에 있습니다.

R2 미션은 두 개 이상입니다. 다음은 R2-2 기획안 작성이 이 리포트를 근거로 이어집니다. 다른 미션은 개요의 R2 미션에서 고릅니다. 정식 출품은 출품 양식으로 하고, 완주 체크리스트 6번은 두 번째 미션까지 끝낸 뒤 채웁니다.
